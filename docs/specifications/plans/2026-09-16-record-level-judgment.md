# Record-Level Judgment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: this repo's `CLAUDE.md` mandates `superpowers:subagent-driven-development` for every written implementation plan by default — do not offer `superpowers:executing-plans` as an equal alternative; only fall back to it if the user explicitly asks for inline/in-session execution instead. Steps use checkbox (`- [ ]`) syntax for tracking. (This plan was executed inline in the session that wrote its spec, which had no superpowers skills installed, and its later tasks were shaped by review rounds on the pull request — recorded here as the historical task log the plans tree is for, in the same way as [`2026-09-07-recommendation-judgment-token-cost.md`](2026-09-07-recommendation-judgment-token-cost.md).)

**Goal:** Stop paying for the same taste question more than once. Judgments already survived a scheduled re-crawl, but the identity they hang on — `item_key`, a hash including the store URL — made one record three separate paid questions: a re-slugged product page, a second shop stocking it, and each pressing.

**Architecture:** Judgment is billed per *record* rather than per listing, without re-keying the table that stores it. `record_key` (`backend/title_key.py`) is `title_key` one step coarser, dropping the pressing-variant vocabulary a store fences off in a bracket or a trailing segment. `get_unjudged_stock_items` returns one representative per unjudged record; `db.propagate_stock_judgments` copies a record's verdict onto its other in-stock, unowned, unjudged listings. Every reader — the Recommended filter, `get_recommended_stock_items`, the CSV export — goes on matching listing-for-listing, so `stock_item_judgments` keeps its `(user_id, item_key)` primary key, its export format, and needs no migration. Verdicts reach records through `stock_item_identities`, never `stock_items`, because the snapshot table is deleted and rewritten every sync and a join through it loses exactly the re-listing case this exists to catch.

**Tech Stack:** Python ≥3.9, Postgres with RLS-scoped connections, pytest with `asyncio_mode = "auto"`; React + Vite + TypeScript with vitest for the Store tab's filter state.

**Spec:** [`docs/specifications/shaping/2026-09-16-record-level-judgment-design.md`](../shaping/2026-09-16-record-level-judgment-design.md)

**Branch:** `claude/wizardly-goldberg-mxvey2`, worktree under `.worktrees/`, based on `origin/main`. Not stacked on anything.

**Before starting:** confirm the baseline is green so any later failure is attributable to this plan.

## Task 1: `record_key`

- [x] Add `record_key(title, artist)` to `backend/title_key.py`: `title_key`'s fold with the pressing-variant vocabulary (`_VARIANT_WORDS`) dropped.
- [x] Drop those words **only** where a store fenced them off — inside a bracketed aside, or in a trailing segment behind a separator. A bare word list folds "Purple Rain" into "Rain" and "Black Sabbath" into "Sabbath", and a false merge here hands a record another's verdict *and* a reason written about a different album.
- [x] Keep the never-empty guarantee: fall back to `title_key(title, artist)` when stripping would leave nothing.

## Task 2: Store and sweep the key

- [x] Add `record_key` to `stock_items` **and** `stock_item_identities`. Both, because the judgment path needs the durable table: `replace_stock_items` deletes and rewrites the snapshot every sync, so a verdict reached through live stock rows goes missing for the re-slug case.
- [x] Compute the value once per item in `replace_stock_items` and `upsert_stock_item_from_release` and write that same value to both tables, so the pair can never disagree about which record an `item_key` belongs to.
- [x] Rename `backfill_title_keys` to `backfill_stock_keys` and have it fill either column across both tables. Key an identity from its live stock row where it still has one — on the release-crawler path the two tables' own titles genuinely differ (`listing_title` against the catalog target's name), and reading each table's own columns would reintroduce the disagreement the live writers avoid.

## Task 3: Bill per record

- [x] `get_unjudged_stock_items` returns one representative per unjudged record, `DISTINCT ON` the group with the lowest `item_key` so repeated runs batch identically; `count_unjudged_stock_items` counts the same groups.
- [x] Anti-join on the *record*, through `stock_item_identities`, with `i.item_key = s.item_key` as a floor so this exact listing having been judged reads as judged whatever the folds do.
- [x] Add `db.propagate_stock_judgments`, scoped to exactly the rows that would otherwise be billed (in stock, unjudged, not owned), newest `judged_at` winning where a record's listings disagree.
- [x] Call it from `_run_judgment_phase` before the counts and after each batch's upsert, each in its own `user_scope` — `app.user_id` is set transaction-locally, so committing inside one scope and carrying on leaves later statements with no RLS identity.
- [x] Carry the count on `stock_judgment_complete` as `inherited`.

## Task 4: Guard the start path

- [x] Make both guards reach across Machines. `db.advisory_lock_held` reads `pg_locks` for the sync lock; a judgment run held `pg_try_advisory_lock(JUDGMENT_LOCK_NAMESPACE, user_id)` for its lifetime, released in `_run_judgment_phase`'s `finally`.
- [x] Serialize the whole check-and-assign under one asyncio lock, since the cross-Machine reads await and the task assignment is what makes the running check true.
- [x] ~~Return `{started, running, stock_sync_running}`~~ → `{started, stock_sync_running}`; see the merge note below.
- [x] Render the rejection in `handleRefreshRecommendations`, guarded on the status-write counter so a slow response cannot talk over newer progress.

**Merge note (2026-09-16).** The second and third items above were undone when `main`'s stop-a-run change ([`2026-09-16-stop-recommendation-run-design.md`](../shaping/2026-09-16-stop-recommendation-run-design.md)) was merged into this branch. It solves the per-user duplicate-start problem with a claimed `stock_judgment_runs` row instead of an advisory lock, which also survives a worker wedged in a blocking call — a case no session lock can recover from, because nothing can reclaim it. So the judgment lock, its release `finally`, its dedicated connection and the asyncio start lock all went out, and `start_judgment_only` takes main's claim. The sync guard and its `stock_sync_running` field stay: the claim cannot answer them, since that refusal writes no row and runs before the claim on purpose. The fourth item stands, though the fence is now main's own sequence counters rather than the status-write counter.

## Review rounds

The pull request drew several rounds of review, each of which changed the code above. Recorded here because the shape of what shipped is not derivable from the tasks alone:

- **Round 1** — the sync guard was process-local; the backfill put different keys in each table for release-crawler rows; `_SEGMENT_SPLIT` tore apart artist names containing separators; the rejection message promised an automatic refresh that never happens.
- **Round 2** — the cross-Machine read introduced an `await` between the running check and the task assignment, so two clicks for one user could both start; a bare digit counted as a pressing variant; the two sides of the record match bottomed out at different fallbacks.
- **Round 3** — `_judgment_tasks` is a dict in one process, so two Machines could each start the same user's run. This predates the branch but is the same duplicate spend, so it was fixed here rather than deferred.
- **Round 4** — propagation made a run that writes judgments without judging any, which the Recommended filter's `judged > 0` gate could not see.
- **Round 5** — a mixed keyed/unkeyed catalog, which a rolling deploy produces, re-bills a judged record's siblings; the lock acquisition leaked a session when its query failed; the identities index was justified as "nearly free" on a false premise, and measurement showed it is a real trade worth making for different reasons.
- **Round 6** — the artist-prefix test did not fold the punctuation `_artist_punct_fold_sql` folds, so a store spelling "Hall & Oates" against a stored "Hall and Oates" kept the artist in the key.
- **Round 7** — that fold ran *after* the article forms were expanded, unlike the SQL, so "The-Beatles" never lost its article; the lock-release `finally` started after the first await; a slow rejection could overwrite newer progress in the banner.
- **Round 8** — the two sides of the record match still fell back to different things when a key was missing, which was rounds 2 and 5 a third time. Ended the class instead of patching it: both sides now require the key and an unkeyed row is skipped rather than compared. Round 5's fallback, and the sweep-prevents-a-charge reasoning behind it, went with it.
- **Round 9** — four of the five findings were that change's own fallout. The identities index still stored `COALESCE(record_key, title)` while the query had moved to the bare column, so it was unusable; `box set` went into the phrase list `title_key` shares, which would have collapsed a box set onto an ordinary pressing in the Cheapest filter; the sweep's comment and the design doc still described the removed fallback; and the `item_key` floor test cleared the stock row's key too, so it passed with the floor deleted.
- **Round 10** — one real bug and the rest of round 8's stale text. The sweep reconciled an identity only when its *own* key was missing, so an identity keyed while its item was out of stock and then restocked unkeyed by an old binary stayed permanently unequal to its stock row — the re-billing this design exists to prevent, made permanent. The sweep now keys the stock rows first and copies each identity's key from its live stock row, selecting on disagreement rather than on a NULL; the identities' NULL-key partial index is dropped, having lost its only reader. The stale text was the propagate-before-counting rationale (the billable set already excludes a judged record whether propagation ran or not — what the order buys is `inherited` and the per-listing rows the filter matches on), the sweep-ordering test's rationale, two test docstrings still describing the fallback, and the separator comment still listing a comma.
- **Round 11** — round 10's own fix, one layer down. The sweep reads a row, folds it in Python and writes it back, and the crawl worker pool holds no part of the stock-sync lock, so under `READ COMMITTED` a worker can commit in between; running both passes in one transaction buys atomicity, not isolation. The unconditional `UPDATE` therefore wrote the fold of a title the row no longer had, and the identity pass copied that stale value across — leaving the two *equal*, the one state round 10's disagreement test can never notice again. Both writes are now conditional on the row still holding what the sweep read, with one test racing each pass. The round's other finding, that this log stopped at round 7, is what this section now answers.
- **Round 12** — the merge's own fallout. Taking `main`'s arrangement of `_run_judgment_phase` put the opening `stock_judgment_started` broadcast back outside the `try`, and that `finally` now closes the run's claimed row rather than releasing an advisory lock — so a cancellation landing on that await left the row saying `running`, refusing the user every Refresh until the heartbeat went stale. Round 7 had fixed exactly this against the lock; the mechanism changed and the hazard did not, and the fix went out with the mechanism. Also a stale line in the backfill docstring, still saying a shared NULL `record_key` would hand every unkeyed row one verdict — true of `title_key`'s grouping, not of the judgment path, which requires the key on both sides and compares an unkeyed row against nothing.
- **Round 13** — the cheap version of the sweep, finally abandoned. Rounds 10 and 11 both asked "which keys are missing", and a missing key turns out not to be the dangerous way a stored one goes wrong: an old binary's `ON CONFLICT DO UPDATE` names neither fold key it does not know about, so it *preserves* them while `listing_title` moves, leaving a row keyed from a title it no longer has with nothing NULL to mark it, and an identity holding the same stale value so the disagreement test sees agreement. A false merge, permanently invisible. The same writer also holes round 11's compare-and-set: it changes `listing_title` while leaving `record_key` NULL, so a predicate reading the key columns still matches and the sweep overwrites the newer title. The sweep now recomputes every row and writes only where the source fields still read as it found them; all three NULL-key partial indexes go with the query that used them, and both callers run it off the event loop, since the steady-state cost went from ~23 ms to ~850 ms at 9,000 rows.
- **Round 14** — two findings, both about the boundary with other writers rather than the folds. The sweep's two passes shared a transaction, so it held `stock_items` row locks while reaching for `stock_item_identities` — the opposite order to `upsert_stock_item_from_release`, and a cycle Postgres resolves by aborting somebody: a lost crawl result, or a judgment run failing in front of the user. There is no order to agree on, since `replace_stock_items` deletes its stock rows before upserting identities and so disagrees with the other writer already; the sweep commits between its passes instead and holds neither lock across the other. Separately, `inherited` existed only on the SSE event, which reaches subscribers of the Machine running the job — so a client polling from the other one was told a run that spent nothing checked nothing. It is now a column on `stock_judgment_runs`, carried by the progress and finish writes, reset by a claim, and returned on the status endpoint.
- **Round 15** — five findings. The substantive two: the artist-prefix test applied one fold on each of two paths — punctuation-only, with an accent-only fallback — so a name spelled differently in *both* ways matched neither, and `record_key("Beyonce and Jay Z - Album (Red)", "Beyoncé & Jay-Z")` came out as `beyonce jay z`, the artist's name with no title in it, against `album` for the same record written plainly. It applies both folds now. And a stale key still reached the judgment queries in the gap between a sweep returning and those queries running, where being non-NULL is enough to be compared — grouping a listing under a record it is not, and handing it a verdict the `item_key` floor then keeps for good. A `BEFORE UPDATE` trigger on each table now nulls a fold key whose source fields moved without it, so the write that creates the hazard is the write that clears it; the sweep's recompute stays for rows already stale from before it. The other three were stale text the round-13 change left: the sweep's log wording, the schema comment on `title_key`, and the store-cheapest-filter spec's claim that a NULL-key partial index makes the sweep a lookup — an index that change had dropped.
- **Round 16** — a red CI check and three findings. The check was mine: making `StockJudgmentRun.inherited` required broke the typed `run()` fixture in `recommendationRunStop.test.tsx`, and my local `npx tsc --noEmit` did not see it because CI runs `npm run build` (`tsc -b`), which type-checks the test project too. The field is optional now, which is also the honest typing — during a rolling deploy the Machine answering the request may not be running the binary that added the column, which is why every read of it already goes through `?? 0`. Of the findings: the per-batch progress write persisted the count as it stood *before* that batch's fan-out, so a run cancelled between the commit and the next checkpoint closed on a number short by one batch, with the rows committed — it now writes again after the fan-out, in the same transaction. `running` and `stock_sync_running` are not mutually exclusive (a sync may start while a user's run is going), and the sync branch won, sending the user to wait out something that is not what will refuse their retry; the run's message wins now. And two design-doc guarantees still described the sweep as one transaction, which round 14 split.
- **Round 17** — a regression round 13 introduced into the case this whole design exists for. Recomputing *every* identity meant recomputing the ones with no live stock row, and those are precisely the ones whose key cannot be re-derived: a release-crawler identity holds the fold of the marketplace's name for what it matched while its own `title` is the catalog target, and the two genuinely differ. Re-folding from the title overwrote a valid key, so an item returning at a new URL under the same marketplace name found no judged identity and was billed again — the re-listing leak. It keeps a non-NULL key when there is no stock row now, and leaves staleness there to the trigger, which nulls the key when the identity's own title moves. Also raised, and deliberately **not** fixed: the record group's artist half is `_artist_sort_sql`, which folds `&` and the article but not accents or apostrophes, so `Beyoncé` and `Beyonce` stay two billable groups. Recorded as a Deferred section in the design doc with both candidate fixes and what each costs.
- **Round 18** — round 16's finding one step earlier. The run's *first* fan-out commits before the billable set is counted, and everything between can raise — two queries and a taste read — while the error close carries no count, so a count written only at the pre-flight checkpoint left the row saying 0 with those judgments committed. Now written in the same transaction as the rows, like the per-batch one.
- **Round 19** — two more false-merge routes. `_SEGMENT_SPLIT` still fenced on `/` and `|`, so `record_key("Black / Gold") == record_key("Black")` and `record_key("Red | Blue") == record_key("Red")` — the same failure that took the comma out, and the slash is worse, since a two-sided or double-album title is exactly where one appears. Both are gone; the dashes and brackets stay. And the identity pass copied its live stock row's key even when that key was NULL, which the trigger produces whenever an old Machine moves a title after the stock pass has committed — erasing a key the identity still held correctly, and setting up the orphan branch to re-derive it from the catalog title if the row then went out of stock. It leaves the identity alone until the stock row is keyed.
- **Round 20** — three things. The initial propagation wrote to `stock_item_judgments` before proving the claim, where every batch below does the reverse; the lock that check takes is what orders a judgment write against a clear or an import, and the sweep ahead of it is now long enough to be taken over in. Checks first and returns silently now. Also two passages I had reported fixed and had not: the store-cheapest-filter spec's partial-index claim (that edit sat after a failing assert in the same script and never ran) and the design doc's propagation bullet (a different passage from the one I did fix). Both corrected, and each verified in the file afterwards rather than trusted to the script. And the identity pass's compare-and-set still read only the key, seven rounds after the stock pass's was widened to its source fields: an old writer moving an identity's title leaves a NULL key NULL, so the predicate matched and wrote the fold of a title the row no longer had — which the keep-what-is-there branch would then preserve for good on an orphan. It fences on `artist` and `title` now.
